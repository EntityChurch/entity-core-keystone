# CONTRACT-LAYERS — what binds every peer, what binds a keystone peer, and what binds this repo

**The question this answers.** This repo enforces a lot of things. Some of them come from the
protocol and bind every implementation in the ecosystem. Some of them are decisions *we* made about
the peers *we* generate, which no other implementation owes. Some bind neither and are house rules
for the repo itself. Until now that distinction lived in the heads of whoever wrote each gate, and
in a handful of well-written directory READMEs that each got it right independently.

Getting it wrong is expensive in both directions. Publishing an internal decision as though it were
conformance is an overclaim that propagates to every implementer — this repo is the conformance
anchor, so a rule we invent reads as a rule the protocol imposes. Treating an internal contract as
*less real than* conformance is the opposite error, and it is the one measured here: the single
verification axis with no external authority is the only one whose checks went stale.

**The short version.**

- **A ground-up peer written by anyone owes Layer 1 and nothing else.** Passing Layer 1 makes it a
  conformant entity-core peer, full stop.
- **A peer this repo generates owes Layer 1 + Layer 2.** Layer 2 is not conformance and never
  gates anyone else. It is the difference between *a peer* and *a peer the extension generator can
  build into*.
- **Layer 3 binds this repo and no peer at all.**

---

## Layer 1 — Core protocol conformance

**Binds:** every implementation, everywhere, keystone-generated or not.
**Authority:** `entity-core-protocol` (architecture) for the spec; `entity-core-go` for the
`validate-peer` oracle; architecture for the fixture corpora.
**Our role: consumer.** `GUIDE-CONFORMANCE.md` §7.0 states it outright — *"`entity-core-keystone`
authors none of these"*, and asking us for a vector *"asks the scorer to write the exam."*

| Axis | What it asks | Where the authority is |
|---|---|---|
| **S4** conformance | the published number | the oracle, `--profile core`, pinned by content digest |
| **origination** | does the peer originate outbound | the *same* oracle — `-category origination -reference-peer` |
| **S2** codec / crypto-agility | do our bytes match the corpus | architecture's vendored corpora, digest-pinned |

**Degrees of freedom: zero.** Spec-vs-implementation divergence is a defect in the implementation.
Spec-vs-oracle divergence is a *finding*, routed to architecture as a handoff, never patched here.
The oracle is never doctored. The spec snapshot is immutable once stamped.

**What we may not do is as important as what we must.** We do not author a check, a corpus, or a
vector. Where we have pinned a *reading* of a normative rule (Layer 2b below), the pin is explicitly
subordinate: the spec is normative, the oracle's vector is the measurement, ours is a transcription
that loses to both.

## Layer 2 — The keystone peer contract

**Binds:** peers generated by this repo.
**Binds nobody else.** A third-party peer that satisfies Layer 1 and none of this is a conformant
peer. It simply is not a *keystone* peer, and the extension generator cannot build into it.
**Authority: ours.**

This layer exists because the protocol deliberately stops short of things a fleet of 46
implementations still has to agree on, or that a generator has to be able to rely on. Core protocol
draws its boundary where interop ends — that is the right boundary for a protocol, and it leaves
real decisions unmade. Layer 2 is where we make them, for our own peers, in the open.

**Four kinds live here, and they differ in one thing that matters: what happens when upstream
moves.** The repo has been getting these right one directory at a time without ever writing the
taxonomy down.

### 2a — Convention filling a spec-delegated gap

The spec pins an **invariant** and explicitly leaves the *form* to the implementation. We pin one
form so 46 peers are operationally identical instead of 46-way divergent.

- `protocol-generator/shared/seed-policy/` — §6.9a pins the invariant; *"the cross-peer file format
  and CLI convention are keystone's"*.
- The peer startup convention: `--name NAME` for persistent identity, `--validate` for the
  conformance handlers, `--debug-open-grants` (deprecated).

**Supersession:** the spec wins on any overlap; flag the drift. If architecture later specifies the
form, ours is deleted, not reconciled.

### 2b — Transcription of a normative rule

The spec is normative and its prose admits more than one implementation reading. We pin **one
reading** so that fixing N peers does not manufacture N readings — which is how the last one of
these got created.

- `protocol-generator/shared/scope-matching/` — the F40 typed scope-match contract, with a runnable
  `reference.py` and a portable vector file, and its authority order stated in its own README.

**Supersession:** *"the spec is normative; when the oracle ships the vector it is the measurement;
this directory is neither."* A transcription is a scaffold with an expiry date.

### 2c — Derived drift target

Harvested from a reference implementation to diff against. Non-normative by construction.

- `protocol-generator/shared/test-vectors/type-registry/` — harvested from the reference peer's
  registry as a render/diff target.
- `protocol-generator/<lang>/reference/` golden files.

**Supersession:** re-harvest. **Never edited to mask a regression**, and never treated as a
determinism guarantee.

### 2d — An additional obligation the protocol deliberately does not impose

**This is the genuinely new category and the one the taxonomy was missing.** The three above all
derive from something upstream — an invariant, a rule, an implementation. This one does not.

Core protocol says a peer resolves a path to a handler and dispatches. **It does not say a third
party can install one, and it should not:** a peer that will never host an extension is complete
without it, requiring it would make conformance harder for zero interop gain, and nothing about it
is observable on the wire. But the extension generator cannot install into a peer that does not
expose a seam, so the requirement has to exist *somewhere*. That somewhere is here.

This is the **peer host contract** — `docs/spec/SPEC-KEYSTONE-PEER.md`, H1–H9 at v1.0: handler
installation after construction through a public registration surface that is reachable by dispatch;
emit-consumer registration; the composition surface as the only public mutation path; both consumption
modes reachable across the packaging boundary; the platform bindings declared per language; the
connection's frame budget readable by a handler body; a delegable evaluator; execution context on
events; a public path predicate. Its provisional successor — run · embed · extend, certified per peer by
one shared driver — is `protocol-generator/shared/peer-contract/CONTRACT-DRAFT.md`.

**Ownership is settled** (operator, 2026-09-02): the contract is keystone's, negotiated directly
with `entity-system-generator` as the consumer. Architecture is not a party to it. What stays
architecture's and normative is a different subject — `SDK-OPERATIONS` §11.6, the handler-install
contract that binds every SDK, and the proposed `GUIDE-CONFORMANCE` §7d, the check class — because
those bind everyone, not only us.

**Supersession: none. Nothing upstream can retire this, which is exactly why it carries the
highest rot risk in the repo** — see the rule below.

**Status: taken, and executable.** v1.0 is pinned by digest and gated; the v2 draft ships with its
suite (`tools/peer-contract/`), and one peer of 46 is certified against it. Each peer's `profile.toml`
declares its v1.0 bindings in an **`[extension_host]`** block — `declined` is a
value and silence is not, because a substrate that legitimately cannot host an extension is stating
a fact about itself, exactly as `codec_strategy` does. *(The key is `[extension_host]` and not
`[host]` because `[host]` already means something else in this tree — the language hosting an FFI
seam — and the hybrid-FFI peers will want it.)*

## Layer 3 — Keystone project discipline

**Binds:** this repo. No peer, ours or anyone's.
**Authority:** ours, some of it delegated from ecosystem ADRs.

| Group | Gates | Asks |
|---|---|---|
| Publication honesty | `check-set-gate` · `pin-gate` · `coherence-gate` · `link-gate` · `skip-provenance-gate` | is a published number comparable, anchored, self-consistent, and not resting on an unexercised check |
| Build reproducibility | `containers-gate` · `koji-pin` · `images-audit` · `cold-build-gate` | can an adopter rebuild this from scratch |
| Harness interface | `harness-gate` · `run-axis-sweep.sh` | does every peer's entry point honour the same interface, and is every axis actually swept |
| Spec boundary | the `lint` spec-data SHA-256 pin check | has an immutable normative input been edited |

Several of these enforce Layer 1 *honesty* without being Layer 1: the oracle pin, the check-set
digest and the skip provenance are all about whether we may publish a number, not about whether a
peer conforms. That distinction is why a peer can be conformant while our matrix is wrong, which has
happened, and is what these gates exist to catch.

## Where S3 sits, and the rule the whole map turns on

**S3 — two-direction loopback interop — is Layer 3 authority over Layer 2 content.** It verifies
that generated peers actually talk to each other, which is a keystone property; its assertions are
hand-written here, with no oracle behind them. Under `GUIDE-CONFORMANCE.md` §7.0 that is row three —
an impl-internal test, *"that repo, its own concern"* — which is explicitly legitimate and
explicitly not conformance. The guide's §7 surface map says the rest of it: impl-internal
correctness is the implementation's own concern, and **"wire conformance doesn't exempt it."**

So an internal gate is not a lesser gate. But it does carry a specific, measured hazard:

> **A check with an external authority behind it moves when that authority moves, and something
> makes the move visible. A check we wrote ourselves has nothing watching it.** An oracle re-pin
> shifts `check_set_digest` and re-censuses 46 peers. A corpus supersession changes a digest. A
> hand-written assertion drifts silently against the peer it is meant to check, and then fails in
> the direction that looks like a peer bug.

Measured: S3 was the only axis of four whose checks had gone stale — `apl`'s passed an absolute path
where the peer takes a stripped one, `sql`'s never signs its post-auth requests, and both peers were
`756 · 0F` on the wire the whole time.

**The forward-looking consequence is about Layer 2d, not about S3.** The host contract is the first
thing this repo has authored that has *no* upstream referent at all — no invariant to defer to, no
rule to transcribe, no reference implementation to diff against. By the rule above it will rot
faster than S3 did, and it starts with 45 of 46 peers unmeasured.

**Therefore: a Layer 2d requirement ships with its executable gate or it does not ship.** Not a
census document, not a table, not a source read — a check that runs per peer and can go red. The
evidence for that standard is already in: four peers were nominated as satisfying H1 from source
reads by three different seats, and three of the four were wrong, each at a different packaging
boundary — the class in C++, the assembly in C#, a live public entry point onto a container nothing
reads in Julia. Two of those wrong nominations were ours.

## Reading the map

| You are | You owe |
|---|---|
| Writing a ground-up peer in any language | **Layer 1.** Nothing here obliges you to anything else. |
| Consuming a keystone-generated peer as a library | Layer 1 + Layer 2, and Layer 2d is what you are relying on |
| Working in this repo | all three, and the first job on any new rule is to say which layer it is in |

**When adding a rule, name the layer before writing the enforcement.** A rule that cannot name one
is either an unrouted spec finding (Layer 1, and it belongs upstream) or a preference.

**And name the KIND before writing the artifact — `VERIFICATION-ARCHITECTURE.md`.** This file answers
*which layer does this rule bind*. It does not answer *what is this check allowed to conclude*, and
that gap is how `tools/put-probe` came to drive implementation across 46 peers while belonging to no
declared category, no axis and no README. The sibling document names the three kinds a verification
artifact can be — a census **probe**, a **transcription** of one normative reading, an **independent
check** — with the obligations and the expiry rule for each, and the constraint that makes the third
kind a second *measurement* rather than a second *authority*.
