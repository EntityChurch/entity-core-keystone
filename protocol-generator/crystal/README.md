# entity-core-protocol-crystal

A **Crystal core protocol peer** for the Entity Core protocol (**v0.8.0 / V8**), generated by
the [`entity-core-keystone`](../../README.md) `/entity-rosetta` pipeline. The cohort's
**Ruby-overfit check** (T3, corroboration) — Crystal reads like Ruby (blocks, `PascalCase`
types, `snake_case` methods, exceptions, a `spec` test framework) but is a **compiled,
statically-typed, fixed-width-integer, LLVM-backed** language with **CSP fibers** instead of
MRI threads + GVL. Its job is to prove the generator derives the wire/runtime-touching axes
from the profile, not from the Ruby peer's templates.

**Conformance badge:** `validate-peer --profile core` — **Result: PASS · 682 total · 0 FAIL**
(292 pass / 294 warn / 96 skip; all 96 skips are §9.0 auto-allowlisted extension carve-outs,
none fail-counting), oracle **`entity-core-go @cc1970f`** (core-gate fingerprint `8261a033…`).
Codec: **71/71** byte-identical to `conformance-vectors-v1`; §9.5 **53/53** type floor;
genuine 2-of-3 multisig accept-path (the oracle's own `valid_2of3_peer_signed_accepted` runs
live + PASSES, not skipped). Robustness: the S4 gate is **20/20 crash-free under repeated
concurrent load** after the graceful-shutdown fix (see below). Full report:

**Status:** `0.1.0-pre` — publish-ready, **not yet published**. Tracks Entity Core spec-data
**v0.8.0 (V8)**; codec corpus v0.8.0. The core wire contract is byte-unchanged across the
V7→V8 cutover.

## Honest framing (ADR-0012)

This is a **corroboration / generator-robustness** peer, **not** spec-discovery. The
discovery well is dry on the current wire surface (the crypto-availability / integer-model /
memory-model / string-model axes are saturated across the cohort). A green verdict here is
**cohort-consistent, not independent convergence**: the `validate-peer` oracle and the
type-registry vectors are the Go author's artifacts, so one peer passing one author's vectors
is generator robustness on a fresh substrate — not a second independent witness to the
protocol bytes.

## The point of this peer — the Ruby-overfit check

Crystal's surface resembles the cohort's Ruby peer, but five **wire/runtime-touching** axes
diverge — exactly the places a Ruby-template overfit would go wrong. The generator got each
from the Crystal profile, not from Ruby:

| Axis | Ruby peer | Crystal peer (this) |
|---|---|---|
| Integer model | arbitrary-precision `Integer` (`native_bignum`, no head-form trap) | **fixed-width `UInt64`** — carries the CBOR uint64 head-form + the `[2^63, 2^64-1]` self-test (overflow *raises* by default; wrapping is `&+`) |
| Ed25519 | stdlib `openssl` (has Ed25519 **and** Ed448) | **direct in-process libsodium `lib`/`fun` C binding** — Crystal stdlib `OpenSSL` has *no* PKey/Ed25519 surface (verified absent; beware web snippets claiming otherwise) |
| SHA family | native SHA-256/384/512 via `openssl` | native `Digest::SHA256`/`SHA512`; **SHA-384 via `OpenSSL::Digest`** (no native `Digest::SHA384`) |
| Ed448 agility | **native** via `openssl` | **deferred** (libsodium has no Ed448; future FFI-hybrid via `libentitycore_codec`) |
| Concurrency | MRI OS-threads + GVL | **CSP fibers + `Channel`s**, single OS thread (structural §4.8 store-safety, no mutex) |

The codec is **hand-rolled canonical CBOR** (no Crystal shard does ECF length-then-lex +
shortest-float incl. float16 + recursive major-6 tag reject; `crystal-cbor` is RFC-7049,
insertion-order, and silently *skips* tags). Byte-strings vs UTF-8 `String` are distinct
static types, so ECF map keys are modeled as arbitrary `EcValue`s (incl. byte-string keys) —
a distinction Ruby's UTF-8-`String` model hides (see A-CRY-007).

## Concurrency & the graceful-shutdown fix (a durable peer-build lesson)

Crystal's model is CSP fibers over channels on a single OS thread by default (no GIL
construct — the scheduler simply doesn't preempt between yield points), so blocking socket IO
yields via the event loop and a **fiber-per-connection** peer is genuinely concurrent for the
IO-bound §4.8/§4.9 workload. Multithreading (`-Dpreview_mt` / Execution Contexts) is still
*preview* in Crystal 1.20 and is **not used at core**.

Because the S4 harness reaps the host with `SIGTERM`, and Crystal 1.20's Execution-Contexts
scheduler is a preview, an **unhandled** `SIGTERM` could interrupt the fiber scheduler
mid-schedule → an intermittent `Thread#execution_context cannot be nil` crash (~1 run in ~15
under repeated load). The fix: the host **traps `SIGTERM`/`SIGINT` and closes the listener**
for a clean, scheduler-intact exit; `run-s4.sh` reaps gracefully (TERM, then wait for exit).
Verified **0 crashes / 20 consecutive full `--profile core` runs**. Lesson for the family: a
fiber-scheduler peer on a preview scheduler needs a graceful signal handler, or it flakes
under a kill-based harness (the analogue of the Zig TCP_NODELAY lesson).

## Build / test / run (container-bound)

All work happens inside the pinned `entity-core-keystone/crystal-toolchain:latest` image
(Crystal 1.20.2 / LLVM 20.1.8 / libsodium 1.0.18). The core peer has **zero runtime shard
dependencies**; the conformance run is sealed offline (`--network=none`).

```sh
# codec gate (71/71 wire-conformance + head-form + Ed25519 accept-path)
bash protocol-generator/crystal/run-s2.sh        # → crystal spec, all green

# conformance gate (validate-peer --profile core, 0-FAIL)
. tools/podman-caps.sh
podman run $PODMAN_RUN_CAPS --rm --network=none -v "$PWD":/work:Z \
  entity-core-keystone/crystal-toolchain:latest \
  sh /work/protocol-generator/crystal/run-s4.sh -profile core

# the peer host
crystal build --release bin/entity-core-peer.cr -o entity-core-peer
./entity-core-peer --port 7777 --name mypeer [--validate]
#   loads ~/.entity/peers/mypeer/keypair  (PEM: base64 of a 32-byte Ed25519 seed)
#   prints:  LISTENING 127.0.0.1:7777 peer_id=…
```

## Crypto floor & agility

- **Ed25519 + SHA-256** (the conformance floor): native. Ed25519 via a direct in-process
  libsodium C binding; SHA-256/512 via stdlib `Digest` (pure Crystal). No shard dependency.
- **Ed448 / SHA-384** (agility higher bar): **deferred**. libsodium has no Ed448; the
  documented future path is hybrid-FFI via `libentitycore_codec` (`ec_ed448_*`) as an opt-in
  sub-library, so the shipped default peer stays self-contained.

## Publishing

Crystal has no central package host; shards resolve from git repos by `v`-prefixed semver
tags. "Publishing" = a git tag (deferred to the operator, per cohort convention). The shards
id is `entity_core_protocol` (snake_case); the keystone peer id is `entity-core-protocol-crystal`.
