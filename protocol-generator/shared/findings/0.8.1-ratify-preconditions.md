Strip the finding IDs and the amendment is **three unrelated things under one label**, each needing a

## 2. The behavioral delta for core peers

Arch's framing is that 0.8.1 is non-functional hardening. We checked every delta against live peer
source rather than against the amendment text. **It is not extension-only.**

### 2a. Behavioral, and the cohort does not comply — 2

**F40 (§5.2 typed scope matching) — confirmed violated.** `path-scope` dimensions (handlers,
resources) canonicalize to absolute paths; `id-scope` dimensions (operations, peers) must compare as
**literal identifiers**, and "the two MUST NOT be interchanged."

Cohort peers route **all four** dimensions through path canonicalization. Verified structurally
identical in two independent peers:

- Python — `check_permission` → `_matches_scope` → `_covered` → `_canon`, call sites passing
  `operation`, `handler_pattern`, `target_peer` (`peer/capability.py`).
- Go — `checkPermission` → `matchesScope` → `covered`, call sites `matchesScope(localPeer, operation,
  g.operations)` and `matchesScope(localPeer, targetPeer, peers)` (`peer/capability.go`).

`operations` and `peers` are id-scope dimensions and are being canonicalized in both. The scope
*types* are declared correctly in every peer's type registry, so this is not a missing-type problem —
it is a **matching-time typing** problem, exactly the shape F40 names. A shape scan across a diverse
10-peer sample (go, rust, c, java, typescript, haskell, ocaml, csharp) finds the same construction;
given the shared generation lineage we expect it cohort-wide, and §8 quantifies it.

**Honest scoping.** In the common case the canonicalization is *symmetric* — value and pattern
transform alike — so the comparison still lands correctly and this does **not** surface as a FAIL
today. It bites where the two sides canonicalize differently. That is precisely the latent class F40
was written for ("two impls guessing the typing diverge on ALLOW across a peer boundary"), and
precisely why it needs a vector rather than an assumption. **We are not reporting a live ALLOW bug in
the cohort.** We are reporting that the cohort implements semantics 0.8.1 now forbids, and that
nothing would tell us when that starts mattering.

**RT-13b (§6.11 a′ frame write-atomicity) — a new MUST** with no predecessor text: concurrent
dispatch MUST NOT interleave bytes of distinct frames on one connection. Unverified cohort-wide; at
least one peer had the bug (Io, `A-IO-002`), so it is a reachable defect class, not a theoretical one.

## 5. F37 is mis-filed as deferred editorial

The bundle handoff defers "the F37 Appendix-B systemic regen" as editorial. But 0.8.1 **partially
applied F37**: `7558cc4` / `011055f` repointed the `system/peer.peer_id` `type_ref` from
`system/peer-id` → `system/identity/peer-id` at §10.1 and Appendix B, and reconciled the
14-title-vs-15-row bootstrap table.

Not editorial for us, because **`type_system` is a core-gate category**:

- **Every cohort peer renders the old `system/peer-id`** — verified across all 36 peers referencing
  it. **`pd` alone binds both names**, exactly the workaround its own F37 handoff
  (`F37-peer-id-naming-appendix-b.md`) called "a workaround, not a resolution."
- **The oracle still uses the old name at both pins**, including the core type floor `profile.go`
  (`"system/peer-id": true`). `system/identity/peer-id` is **not** in the floor. Confirmed in
  `core/types/core.go`, `core/protocol/connect.go`, `cmd/internal/validate/typesystem.go`.

**So after 0.8.1 the spec and the oracle disagree on F37.** Per our boundaries a spec-vs-oracle
divergence is a finding, not something to route around, and it forks:

- Align the oracle → all 43 peers need a type-registry change (or pd's both-names bind), and the core
  type floor changes, which **moves the core-gate fingerprint**.
- Leave the oracle → the amended spec text is unimplemented and untestable cohort-wide.

Needs an arch decision **before** the snapshot is stamped. We have no preference; we need to know
which branch to generate against. (We are deliberately *not* adopting pd's both-names bind cohort-wide
as a pre-emptive workaround — that would undercut this ask and could be 43 peers of wasted work if
arch reverts the edit.)

This is also the general lesson our own `AGENTS.md` records: **after any "just docs" change, re-verify
the machine-consumed values.** The F37 text is machine-consumed — the oracle is built from it.

## 6. Normative overreach review — are we constraining peers where we shouldn't?

We swept every 0.8.1 MUST against one test: **does this require agreement between two peers
(legitimate interop), or does it dictate a local implementation/deployment choice (overreach)?**

**Result: one item overreaches, in wording only. Everything else is correctly shaped.**

### 6a. The spec already states the right doctrine — twice

§4.10 says it outright:

> **"Values are informative recommended defaults, not normative constants.** The contract is 'enforce
> a finite *declared* bound and reject over-limit cleanly while continuing to serve' — never 'pick
> this number.' A deployment MAY raise, lower, or widen the bounds and stay conformant."

W7 Knob 3 (§5.10) reaches the same shape independently — a deployment MUST *declare* a finite `δ`,
the value is theirs, `δ = 0` reproduces today, and *"two peers with different declared `δ` may
permissibly differ at the boundary."* RT-13a does it for *mechanism*: the store-safety property is a
MUST, but *"the synchronization mechanism is impl-defined"* and a single-threaded runtime *"satisfies
this trivially."*

**Mandate the property; leave the number and the mechanism to the peer.** 0.8.1 mostly honors this.

### 6b. The one exception — §5.9's TTL ratio

> `ttl` and the continuation `chain_depth` ceiling MUST be **distinct** magnitudes with `chain_depth`
> ceiling ≤ `ttl` seed; the pinned **ratio is 8×** — the *ratio*, not the bare seed, is the
> **conformance-relevant quantity**.

The two MUSTs are fine and should stay — *distinctness* and *ordering* are the structural invariant
that de-confounds the two brakes, and neither dictates a value. The problem is the last clause:
calling a specific multiplier "the conformance-relevant quantity" converts a tuning value into a
conformance criterion, which is what §4.10 forbids.

**Why a fixed ratio cannot be universally right — from §5.9's own text.** The section states TTL is
*"fan-out-sensitive"* and that *"one dispatch advances `chain_depth` by at most one causal level but
may spend several TTL across its sub-dispatches."* So the margin needed for the depth brake to fire
before the TTL backstop **is a function of a peer's sub-dispatch fan-out** — a local property. A peer
with heavier fan-out could need more than 8×; a strictly linear one needs far less. **8× is a sound
default generalized from a three-point measurement (go/rust/py); it is not a protocol constant.**

**Nothing is actually forcing it.** We checked the oracle rather than assuming:
`cbxCrossPeerChainBounds` passes on *"cross-peer ping-pong terminated at the GLOBAL ceiling"* — it
asserts a brake exists and the chain terminates, **never at what value**. `64` appears only in
constructing a chain long enough to trip any reasonable ceiling. So the overreach is on paper only and
no peer is constrained today.

That is exactly why it is worth fixing now: **the text claims a gating status the vectors don't
implement, and the next person to write a vector will write it to the text.**

**Suggested re-wording** — keeps every property and the measurement finding, drops the mandated value:

> `ttl` and the continuation `chain_depth` ceiling MUST be **distinct** magnitudes with `chain_depth`
> ceiling ≤ `ttl` seed, chosen so the deterministic depth brake engages before the TTL backstop under
> the peer's worst-case sub-dispatch fan-out. **Recommended default ratio: 8×** (seed 512 at the
> recommended ceiling 64), measured across three impls on the 2026-07-27 run. A deployment MAY choose
> a different ratio to suit its fan-out and stay conformant; the conformance requirement is that the
> depth brake, not TTL, is what terminates a runaway chain.

### 6c. Everything else — correctly scoped

Why each remaining MUST is legitimately a MUST (no local choice exists, because two peers must agree):

| Delta | Why no peer freedom is possible |
|---|---|
| **F40** typed scope matching | An authority verdict must be identical on both sides of a peer boundary; divergent typing = divergent ALLOW. |
| **RT-14** lowercase hex | Path segments compared byte-wise cross-peer; case freedom makes a peer's writes unreadable to others. |
| **RT-13b** frame atomicity | Interleaved frames corrupt the shared connection — no "local policy" reading of a corrupt stream. |
| **F32** 401 vs 403 | The caller must distinguish auth from authz failure. |
| **F48** key_type ordering | Determines which error a client sees for an unsupported algorithm. |
| **RT-6** nonce single-use | Anti-replay security property, correctly scoped to the *interactive* handshake. |
| **A5** reason-code disambiguation | Two mechanisms sharing one reason string is unresolvable by the caller. |
| **A4** `chain_id` single path segment | Wire-format constraint marker path-safety depends on. Mildly restrictive, justified. |
| **§4.10(a)(b)** finite bounds | Mandates *finiteness*; values explicitly non-normative. Exemplary. |
| **§4.10(c)** connection admission | SHOULD, with an explicit carve-out for external admission layers. Exemplary. |
| **RT-8** existence masking | MAY, with a consistency MUST. Correct. |
| **W7** knobs 1/2/3 | Deployment-declared; divergent values explicitly permitted. Correct. |

**0.8.1 is not encroaching on peer autonomy.** One clause needs re-wording to match the doctrine the
spec already articulates well elsewhere.

## 8. What keystone is doing while this is open — we are not blocked

Two different things have been conflated under "the re-run." Separating them:

- **The ratify run** (43 peers, `--profile core`, published oracle-pinned) — **blocked** on §3/§4/§5,
  and running it now would be the vacuous result described above. We are **not** running it.
- **The pre-ratify audit** (quantify where the cohort actually stands on the bucket-B deltas) —
  **fully unblocked**. Needs no snapshot, no oracle change, no arch decision.

**The audit is upstream of arch's vector work, not downstream of it.** Telling arch *"F40 is violated
in N of 43 peers, and here are the M cases where the two sides canonicalize asymmetrically"* is far
better input for designing the vector than *"please write a vector."* It also pre-identifies the
accept-path cases the vector must cover.

In flight now, all derived from the **spec** rather than the oracle (per our boundary rule):

1. **F40 cohort audit** — how many of the 43 share the shape, and critically whether any are
   *asymmetric* (a live ALLOW bug, which would escalate immediately) rather than benign-symmetric.
2. **RT-13b frame-write audit** — which concurrent-dispatch peers write frames non-atomically.
3. **RT-6 / RT-13a / RT-14 audits** — converting §2b from "unknown" to a number. RT-13a scoped to the
   manual-memory substrates where it is reachable.
4. **Peer-side accept-path unit tests** in the direction the oracle cannot cover — the standing
   keystone countermeasure to vacuous green.
5. **Oracle rebuild + core-gate fingerprint re-verification** from go HEAD, plus a toolchain-container
   build sweep — maintenance that would otherwise serialize *after* arch delivers.

**What we are deliberately holding:** fixes. We would rather the F40 remediation be *measured* by a
vector than *asserted* by us, and we are not adopting the pd both-names F37 workaround cohort-wide
ahead of arch's decision (§5). Audit now, fix on vendoring.
