# entity-core-protocol-forth

A **gforth core protocol peer** for the Entity Core protocol (**v0.8.0 / V8**), generated by
the [`entity-core-keystone`](../../README.md) `/entity-rosetta` pipeline. The cohort's
**stack-machine / typeless** peer (#25) — a two-stack, RPN, no-native-record substrate — and
the cleanest **FFI-hybrid** binding in the family: **pure-Forth canonical CBOR** (the
byte-floor's own encoder/decoder), with crypto + SHA sourced over the codec C-ABI
(`libentitycore_codec`) via gforth's **in-process** `libcc` `c-function` — a genuine libffi
call, **no subprocess / FIFO / co-process** (contrast Rexx's `ecnet` daemon), and **native
BSD sockets** in-process.

## What it is — the stack-machine probe

Every prior peer keeps its per-word state in named locals or typed records; Forth has neither
by idiom — computation is RPN over the data + return stacks, with structure carried in
offset-word "structs" over `ALLOT`ed buffers and **explicitly-tagged** values (the substrate is
typeless: a cell is a cell). The probe question (A-FT-000) was **not** "does the byte-floor
express as Forth?" (crypto legitimately doesn't — that's the C-ABI floor's job) but "**do the
language-agnostic phase prompts assume named-variable / typed-record structure the generator
must work around on a stack machine?**" — and the answer is **corroboration**: the recursive
canonical-CBOR encoder/decoder and the §5 capability chain-walk read as native Forth. The two
idioms that made it work, plus the genuine Forth-substrate gotchas surfaced and fixed
(A-FT-010/011: the `>r`/`?do`/`r@` return-stack collision, the `1 0 ?do` empty-container wrap),
are written up in [`status/PHASE-S2.md`](status/PHASE-S2.md) and
[`status/SPEC-AMBIGUITY-LOG.md`](status/SPEC-AMBIGUITY-LOG.md).

Value on the current (saturated) wire surface is generator robustness, not a fresh spec finding
— but the S4 pass **is not vacuous**: seven S4 findings (A-FT-023..028, plus the concurrency
payoff A-FT-025 — a latent `pend-new` missing-return that only concurrent §6.11 reentry
exposed) were **code bugs in the generated peer, fixed here**, not relaxed vectors.

## The FFI-hybrid architecture (pure-Forth codec + C-ABI crypto floor)

No platform CBOR library gives canonical ECF (shortest-float ladder + recursive major-type-6
tag reject + length-then-lex key sort), so the peer hand-rolls it in Forth; crypto (Ed25519,
SHA-256/384) is irreducibly the C-ABI's job. The split:

```
  ┌─────────────────────────────────────────────────────────────┐
  │  Pure-Forth core  (src/*.fs)                                 │
  │    cbor / varint / base58 / peer-id  — §4 canonical ECF      │
  │       (f32/f64 assembled from NATIVE IEEE bits via SF!/DF!;  │
  │        only the f16 leg + shortest-form ladder hand-rolled)  │
  │    capability / capauthz  — §5 chain walk + authz trichotomy │
  │    dispatch / handlers    — §6.5/§6.6 dispatch + §6.11 demux │
  │    store / entity / envelope / tv  — §3.9 store, N4 fidelity │
  │    net                    — native BSD sockets + select loop │
  └───────────────┬─────────────────────────────────────────────┘
                  │  src/ffi/crypto.fs  — in-process libcc c-function
                  ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  C-ABI byte-floor  (libentitycore_codec, built from the      │
  │  ffi-generator/c-abi/entity-core-codec-ffi-c CMake)          │
  │    Ed25519 sign/verify/seed→pubkey, SHA-256 / SHA-384        │
  │    provenance via ec_impl_info(): c 0.1.0 / ecf-c-abi 1.1 /  │
  │    libsodium 1.0.22                                          │
  └─────────────────────────────────────────────────────────────┘
```

The C-ABI floor treats the entity `data` value as opaque pre-encoded bytes, so the peer
**still owns the data-value canonical CBOR** in pure Forth; the 53/53 type-registry byte-diff
proves Forth data-value canon matches the cross-impl encoder. The float tower is materially
easier than Rexx's decimal-model peer: gforth's FP wordset yields real IEEE-754 bits, so only
the f16 half-float leg + the shortest-form ladder are hand-rolled bit arithmetic.

## Build / test / run (in-container, offline)

All build/test/conformance runs happen in the pinned `forth-toolchain` Podman image
(`fedora:43` base + **gforth 0.7.3**, libsodium pre-installed). Every run is sealed-offline
(`--network=none`): the C-ABI codec `.so` + the `libcc` crypto wrapper are byte-built inside
the container (gitignored, not committed); only sources (`src/`, `test/`, `bin/`) + the run
scripts are. There is **no host gforth dependency**. Cap every `podman run` per
[`RESOURCE-CAPS.md`](../../RESOURCE-CAPS.md) (`. tools/podman-caps.sh` → `$PODMAN_RUN_CAPS`).

### Run the peer

```sh
# make ffi first (builds libentitycore_codec + warms the libcc wrapper), then:
gforth bin/peer.fs --port N [--name NAME] [--seed HH] [--validate]
```

`--name NAME` loads the Ed25519 identity from `~/.entity/peers/NAME/keypair` (entity-core PEM =
base64 of a raw 32-byte seed). `--seed HH` (a single hex byte ×32) is a keypair-free test
convenience. `--validate` enables the `system/validate/*` conformance handlers (OFF by default).
`--debug-open-grants` is the deprecated degenerate `default→*` seed policy. On success the peer
prints exactly `LISTENING <bound-port>` on stdout, then serves the select loop. `bin/peer.fs` is
the conformance host driver — test/conformance tooling, not a frozen consumer surface.

## Distribution (`make dist` — a source tarball; no Forth registry)

Forth has **no package registry** (no CPAN/PyPI/crates analogue) and **no module system** — a
peer is a directory of `.fs` files a consumer `require`s. So "the package" is a **source
tarball** (`make dist` → `dist/entity-core-protocol-forth-0.1.0-pre.tar.gz`, ~120 KB) of the
`.fs` tree + `bin/peer.fs` + the run/conformance scripts + `profile.toml` + `status/` +
`LICENSE` + this README + [`CHANGELOG.md`](CHANGELOG.md) + a **[`LOAD.md`](LOAD.md)** load stub.
This mirrors the COBOL / Rexx `make dist` source-distribution convention (no registry inclusion
step). `libentitycore_codec` is a **runtime dependency** documented (its CMake recipe), not
bundled as a binary — the tarball ships the recipe, the consumer builds the `.so`. **Verified:**
`make dist` → extract clean → the packaged `bin/peer.fs` boots to `LISTENING`.

Publishing is an **operator step** (`/entity-rosetta` never publishes): tag a git release
carrying this tree + the tarball; a Forth-community listing is a later, review-gated step.
`repository_url` / `registry_url` are TBD on first publish — the same deferred `0.1.0-pre` state
as OCaml/Elixir/CL/Prolog/Tcl/Rexx.
